# canbus 模块 Vibe Coding 指南（LLM 必读）

> 适用范围：src/canbus/ 及所有与其 ROS 消息、CAN 协议、启动配置直接相关的改动。
>
> 目标：让大模型写出的代码像本项目原作者的增量修改，同时不复制历史缺陷。
> 本文从当前实车基线代码归纳而来；它约束后续改动，不授权重构现有代码。

## 0. 给大模型的执行口令

处理 canbus 任务时，按以下优先级决策：

1. 用户本轮明确需求；
2. 车辆协议原始资料和用户确认的实车结论；
3. 本文件；
4. README.md 中的现行架构、契约、下线功能和风险记录；
5. 修改点附近的真实代码风格。

关键词含义：

- **必须**：不满足就不能交付；
- **应该**：默认执行，除非有明确技术理由；
- **禁止**：不得作为“顺手优化”实施；
- **历史遗留**：可以保留，但不得在新代码中复制。

开始编码前必须：

1. 完整阅读 src/canbus/README.md 和本文件；
2. 阅读将要修改的完整函数，不只看命中行；
3. 若涉及 CAN 帧，阅读对应协议源，例如 docs/ehb-can.md；
4. 若涉及 .msg，全树搜索同名消息、发布者、订阅者和字段读写；
5. 先写清“输入 → 状态 → 安全覆盖 → 编码/发布”的行为链，再改代码。

## 1. 作者风格画像

作者偏好直接、可追踪、贴近设备协议的实现：

- 不追求抽象层数量，优先让一帧 CAN 的来源、位号和去向在一个函数中可见；
- ROS 接线放在 canbus_node.cpp，车辆协议编解码放在 CanbusComply；
- 使用固定周期 Timer 组织业务，不引入线程池、异步框架或复杂事件系统；
- 跨周期状态使用类成员或回调内 static 计数器；
- 状态判断喜欢用显式 if 顺序表达优先级，后写覆盖前写可能具有业务语义；
- CAN 数据使用定宽整数、字节数组、位掩码、移位和显式缩放，少做泛型封装；
- 配置读取失败时使用内置默认值，并用 printf 给出可操作的诊断；
- 注释中英文混用：英文做短标签，中文解释协议、单位、实车结论和冲突；
- 修改倾向小步、局部、保持既有命名和消息契约，不做无关清理。

一句话概括：**协议映射要直白，状态变化要可追踪，安全覆盖要看得见，改动范围要小。**

## 2. 固定架构，不要随意换形

### 2.1 文件职责

| 文件 | 固定职责 | 不应放入 |
|---|---|---|
| src/canbus_node.cpp | ROS 初始化、pub/sub、Timer、参数桥接、周期状态机 | 大段 CAN 位解析、通用框架 |
| src/canbus_comply.h | CanbusComply 状态和协议方法声明 | 模板元编程、无关业务类型 |
| src/canbus_comply.cpp | 车辆控制帧组装、CAN 接收帧解析 | 新 ROS 节点入口 |
| src/struct_type.h | 历史公共枚举/结构体副本 | 无读者的新数据模型 |
| msg/*.msg | ROS wire contract | 仅为显示方便而添加的冗余字段 |
| config.cfg | 少量需换车调节的标定值 | 高频状态、秘密、复杂层级配置 |
| docs/ | CAN 原协议和冲突账本 | 未验证的推测性结论 |

不要为了“现代化”把当前模块整体改成 manager/core/adapter、多线程或模板化 codec。
如确需架构升级，先作为独立提案，不与协议修复混在一个改动中。

### 2.2 当前时间分工是契约

- T1Callback：10 Hz，安全状态汇总、挂钩/鞍座状态机、/ehb_msg 发布；
- T2Callback：20 Hz，车辆控制帧发送、/can_msg 发布；
- main：100 Hz 更新时间并执行 spinOnce()；
- /can_msg 频率被 HMI 健康检查依赖，改频率必须同步检查 hmi/hmi_config.py；
- 两个 Timer 相位不锁，不要假设 T1 与 T2 同拍。

除非用户明确要求改变实时行为，否则禁止移动 T1/T2 的职责或调整周期。

## 3. C++ 写法

### 3.1 语言边界

- 使用 C++11；
- 优先使用项目已有的 ROS1、C/POSIX 和标准库能力；
- 不新增第三方依赖；
- 不引入协程、ranges、concept 或需要更高标准的语法；
- 设备协议字段使用 uint8_t、uint16_t、int16_t、uint32_t 等定宽类型；
- 浮点换算继续使用显式公式，必须在尾注释写清单位和缩放。

### 3.2 缩进与括号

该目录是历史混合格式。新增代码以修改点邻近代码为准，不全文件格式化。
默认形态：

~~~cpp
void CanbusComply::ExampleFunction()
{
    if(condition) {
        DoSomething();
    } else {
        DoFallback();
    }
}
~~~

具体习惯：

- 4 空格缩进；
- 类和函数的左花括号换行；
- if/for/while/switch 的左花括号通常同行；
- 简单赋值允许单行 if，安全优先级或多条件分支必须展开；
- 指针/引用形式沿用 FILE *fp、const char *path、const T &msg；
- 不因个人偏好调整整个文件的空格、空行和 include 顺序；
- 新代码不得复制 Tab、行尾空格、重复 include 等历史瑕疵。

### 3.3 命名

| 对象 | 习惯 | 示例 |
|---|---|---|
| 类 | PascalCase，业务编排类以 Comply 结尾 | CanbusComply |
| 类方法 | PascalCase 动词为主 | VehicleComm、RecvCanData |
| ROS 回调 | 消息/周期名 + CallBack/Callback，保留已有拼法 | CanCommCallBack、T1Callback |
| ROS pub/sub | snake_case + _pub/_sub | can_send_pub、can_comm_sub |
| 消息镜像 | 历史混合命名，保持既有名字 | can_comm_cmd、mCanMsg、mEHBMsg |
| 局部变量 | 简短业务名；同一函数内保持现有大小写 | Brake、Gear、hookpos |
| 枚举值 | 全大写连续单词 | GEAR_N、HOOKOPERATION |
| 定时器 | T1、T2 | ros::Timer T1 |

重要规则：

- 禁止顺手重命名既有标识符，包括拼写错误，如 backwardCambera；
- 新名字要表达车辆域语义，不使用 tmp1、data2 之类无含义命名；
- 协议规定的字段名必须原样保留，即使大小写或英文拼写不理想；
- 若字段是根据中文协议整理出的英文名，必须在 .msg 和文档中注明。

### 3.4 初始化和错误处理

作者喜欢显式默认值和失败回退。新代码必须把这个习惯落实完整：

~~~cpp
uint8_t frame[8] = {0};
frame[0] = 0xFF;
~~~

- 所有成员、计数器、时间戳、局部数组必须初始化；
- CAN 帧先整体清零，再逐字段写入；
- 文件打开、配置读取、ROS 参数读取和输入长度都要检查；
- 配置失败时保留上一有效值或回退内置默认值，并 printf 一次明确原因；
- 不在高频 Timer 中持续刷同一错误日志；
- 当前模块主要用返回值和状态处理错误，不随意引入异常；
- 失败路径必须保持车辆输出确定，不能留下未赋值字节或半更新消息。

## 4. ROS1 编码约定

- 话题使用绝对名，以 / 开头；
- 订阅数据流时保留 ros::TransportHints().tcpNoDelay()；
- 队列大小显式写出：控制指令通常为 1，CAN 接收流可为 100；
- 全局 Publisher + 全局 CanbusComply 实例是现行风格，不为单个需求重构；
- callback 只做转发、镜像更新或小型状态机，大段协议编解码放进 CanbusComply；
- Timer 回调中避免阻塞 I/O、sleep 和重复打开文件；
- 新增参数使用绝对键，先给变量默认值，再调用 ros::param::get；
- 指令新鲜度沿用 sysTime.now - sysTime.msgCanComm 这类显式时间差；
- 超时阈值必须带单位，并说明是“超过”还是“达到”。

跨帧去抖沿用计数器：命中累加、离开清零、计数封顶。阈值必须根据 Timer 频率换算并写明真实时间：

~~~cpp
if(abs(position-limit) < 5) stable_count += 1;
else stable_count = 0;

if(stable_count > 10) {
    state = ACTUATOR_UP_END;  // T1=10Hz,稳定超过1秒才确认
    if(stable_count > 100) stable_count = 100;
}
~~~

## 5. CAN 协议代码约定

### 5.1 发送帧

发送逻辑保持四个连续阶段，禁止交叉穿插：

1. 读取期望命令；
2. 应用急停、制动优先、挡位等安全覆盖；
3. 做范围钳制和合法值检查；
4. 编码完整 8 字节并发送。

每个新帧必须明确：

- 标准帧还是扩展帧；
- CAN ID、DLC、字节序；
- 每个字段的 byte/bit、范围、单位、缩放、偏移和无效值；
- 多条件写同一字节时的覆盖优先级。

协议代码优先保持“一行字段对应一行位操作”的可审计形态：

~~~cpp
mEHBMsg.SomeStatus = (msg.data[2] >> 4) & 0x03;  //3.5-3.6 状态含义
~~~

不要把大量不同语义字段藏进过度通用的宏、反射表或模板中。

### 5.2 接收帧

- 继续使用按 msg.id 分支的显式 switch；
- 每个 case 用花括号形成局部作用域，并以 } break; 结束；
- 读取 msg.data[n] 前必须验证 DLC、帧类型和协议要求的 ID 类型；
- 多字节字段必须明确端序，移位前转换到足够宽的无符号类型；
- 协议有 rolling counter/checksum 时，必须实现校验或明确“仅旁听、不作为控制依据”；
- 遇到 0xFE、0xFF、0xFFFF 等无效值时，按协议选择忽略、置无效状态或保留 raw，不能只写注释；
- 未知 ID 安静忽略，除非任务要求诊断统计；
- 原始帧留档继续使用 rawcommand/rawfeedback，不得改变字段含义。

### 5.3 协议冲突处理

协议表互相冲突时禁止猜测后直接编码。必须：

1. 列出冲突项；
2. 给冲突编号或稳定描述；
3. 说明采用哪一列或哪一份资料；
4. 写明理由和实车待确认项；
5. 同步 docs/、.msg 注释、解析代码和测试向量。

docs/ehb-can.md 是当前 EHB 唯一整理口径，旧版提取结论不能反向覆盖它。

## 6. 安全覆盖与状态机

本模块经常通过代码顺序表达优先级。大模型必须把顺序当作业务逻辑，而不是格式问题。

~~~text
原始控制命令
  → 急停覆盖
  → 制动压制油门/转角
  → 挡位限制
  → 数值钳制
  → CAN 编码
~~~

如果多个分支写同一个字段，例如 can284[2]：

- 必须先列真值表或覆盖表；
- 必须说明“后写覆盖前写”是否有意；
- 不得用看似简洁的 else if 改变多个独立 if 的组合语义；
- 状态值优先使用 struct_type.h 已有枚举；
- 状态码跨包传输时，把数值视为协议，不随意调整。

安全相关改动至少覆盖：手动/自动、D/R/N、正常/急停、指令新鲜/超时、执行器两端/中段/堵转。

## 7. 配置习惯

config.cfg 适合少量、低频、换车时调整的原始标定值：

- 使用 snake_case = value；
- 解释来源、单位、极性、合法范围、默认值和消费方；
- 内置默认值与配置注释一致；
- 相关值成对或成组校验，拒绝半套有效配置；
- 启动时读取一次，成功后可同步到 rosparam；
- 高频周期中不重复解析文件；
- 不把密码、密钥或运行态状态放进本文件。

## 8. ROS 消息是跨包协议

can_msg.msg 和 can_comm_msg.msg 同时存在于 canbus、pnc、simview 三个包中。字段类型、顺序或名称变化会改变 ROS MD5。

修改消息时必须：

1. 全树搜索全部同名副本；
2. 同步字段声明，建议连注释也同步；
3. 搜索所有生产者和消费者；
4. 检查 CMakeLists.txt 是否生成该消息；
5. 整体重编所有相关包，不能只编 canbus；
6. 验证发布端和订阅端的消息 MD5 一致；
7. 检查 HMI、monitor 是否存在字段映射或展示白名单。

禁止为了单端方便修改消息，再依赖另一端“字段碰巧相同”继续运行。

## 9. 注释和日志

优先注释这些信息：CAN ID、byte.bit、端序、单位、缩放、状态码、安全覆盖顺序、频率、去抖时间、协议冲突和实车确认日期。

短注释可以英文，协议和业务原因优先中文：

~~~cpp
//restrain & protection
if(Brake > 0) Throttle = 0;

mCanMsg.controlPanelState = (msg.data[3] & 0x40) >> 6;  //3.7 自动/手动状态
~~~

- 不写“设置变量”“进入 if”之类复述代码的注释；
- 启动配置、回退和拒绝原因用 printf，文案包含对象和实际值；
- 周期回调不打印正常帧；
- 同一持续故障避免每 10/20 Hz 重复刷屏。

## 10. 最小改动纪律

这是实车基线代码。每次任务只改完成功能所需的最小文件和代码段。

禁止顺手执行：

- 全文件格式化或 include 排序；
- 重命名旧变量、回调、消息字段；
- 一次性抽取所有 magic number；
- 一次性封装全局 Publisher 或公开成员；
- 删除历史注释或死代码；
- 恢复 README.md“已下线”章节中的功能；
- 同时重构协议、状态机和 ROS 接线。

允许在本次需求触达的局部范围内修复确定缺陷，但必须说明与需求的关系并补验证。

## 11. 历史缺陷不是编码风格

下列现象存在于当前代码，但不得模仿：

- CAN 数组或成员未初始化；
- 非法挡位留下未赋值字节；
- 不检查 msg.dlc 就读取 8 字节；
- 注释写“忽略无效值”，代码却直接保存；
- checksum/rolling counter 只有字段没有验证；
- 重复 include、Tab 与空格混排、行尾空格；
- 无读者的局部变量和旧 camera 方法；
- 用普通安全分支覆盖更高优先级的急停输出；
- 只依赖手工实车测试，不建立可重复回归。

原则：**保持作者的结构和表达方式，同时提升确定性、输入校验和可验证性。**

## 12. 常见任务模板

### 12.1 新增 CAN 接收帧

1. 从协议源确认 ID、方向、DLC、周期、位序；
2. 确认写入现有消息还是确需新增字段；
3. 在 RecvCanData 增加独立 case；
4. 先做帧合法性检查，再逐字段解析；
5. 每字段一行并标 byte.bit/单位；
6. 处理无效值、checksum、rolling counter；
7. 若改 .msg，执行跨包同步流程；
8. 用正常、边界、无效和坏校验帧验证。

### 12.2 修改发送控制逻辑

1. 画出修改前后的优先级链；
2. 列出所有写目标字节的分支；
3. 对手动/自动、挡位、急停、制动、超时做真值表；
4. 保证 8 字节全部初始化；
5. 验证钳制发生在编码前；
6. 确认不改变另一帧或另一 Timer 的频率；
7. 做字节级期望值断言。

### 12.3 新增配置项

1. 给内置默认值；
2. 在 config.cfg 记录单位、范围和来源；
3. 检查缺失、非数字、越界和组内不一致；
4. 失败时回退并只记录一次；
5. 如需对 PNC 暴露，使用绝对 rosparam 键并检查真实读者。

## 13. 验证和交付

每次都要：

- 查看精确 diff，确认没有无关格式变化；
- 静态检查修改过的 C++；
- 检查数组、成员和失败分支初始化；
- 检查 CAN 字段的位宽、符号、端序、缩放和无效值；
- 检查 Timer 频率、发布频率和 HMI 健康阈值是否一致；
- 搜索被改标识符或字段的所有读写者。

完整 ROS1/车载环境至少执行：

~~~bash
catkin_make --pkg canbus
rostopic hz /can_msg
rostopic hz /ehb_msg
rostopic echo /can_msg
rostopic echo /ehb_msg
~~~

修改跨包消息时，清理相关旧产物并重编 canbus、robot、simview 及其他真实消费者。

大模型交付时按以下顺序汇报：

1. 行为结果；
2. 协议依据和 ID/位号；
3. 安全优先级、超时和失败回退影响；
4. .msg、参数、频率和跨包契约影响；
5. 实际执行的验证；
6. 未验证项。缺 ROS、车辆或协议信息时必须明说，禁止假称通过。

## 14. 提交前自问

- 是否读了完整函数和协议源？
- 是否误把历史 bug 当成作者风格？
- 每个发送字节是否在所有路径确定赋值？
- 每个接收字段是否验证 DLC、端序和无效值？
- 安全覆盖顺序是否被无意改变？
- 独立 if 改成 else if 后，组合语义是否变化？
- Timer 或话题频率是否影响 HMI 和其他消费者？
- 消息副本和所有读写者是否同步？
- 是否恢复了已下线功能？
- diff 是否只包含本任务需要的内容？
- 是否诚实区分“静态检查通过”和“实车验证通过”？

只有这些问题都有明确答案，才可以交付。
