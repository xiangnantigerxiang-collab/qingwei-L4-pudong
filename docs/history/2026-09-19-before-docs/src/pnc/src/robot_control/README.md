# robot_control 模块说明

该目录实现 `control_node`：20 Hz 接收规划、定位、CAN、任务和交通灯状态，
生成 `/control_msg`，并发布用于诊断的 `/acc`。这里记录文件职责和主流程，便于后续按
业务边界定位修改点。代码格式和改动纪律仍以 `src/pnc/README.md` 为准。

## 文件职责

| 文件 | 职责 |
|---|---|
| `control_node.cpp` | ROS 薄入口：订阅、发布、20 Hz 调度 |
| `control_comply.h` | 控制编排接口、输入快照和跨周期状态 |
| `control_comply.cpp` | 路径预处理、围栏、主控制流程和横向控制入口 |
| `longitudinal_acc_control.inc` | 可选 ACC/AEB 计算，由主实现包含进同一翻译单元 |
| `longitudinal_speed_control.*` | 期望加速度、基础油门/刹车分配 |
| `lateral_reverse_control.*` | R 挡预瞄点与转弯半径控制 |
| `stanley_controller/*` | D 挡 Stanley 与纯追踪前馈融合 |

## 运行数据流

```text
/plan_path_msg ──路径过滤/样条/曲率──┐
/navigation_msg ──车辆位姿与速度─────┤
/can_msg ──挡位/反馈转角──────────────┤
/path_plan_status、/task_plan_msg ────┼─> VehicleControl() ─> /control_msg
/camera/tl_status ──交通灯去抖────────┤
/perception ──可选 ACC/AEB────────────┘

fence.csv ─> FenceAlarm() ─> FenceWarning ─> 下一周期安全覆盖
```

`control_node` 当前每周期的调用顺序是：

1. `VehicleControl()` 计算本周期控制量；
2. `FenceAlarm()` 更新电子围栏状态；
3. `PublishMessage()` 发布控制量；
4. 发布 `acc_msg` 诊断信息。

因此 `FenceWarning` 对控制量的影响天然晚一个控制周期。此处只记录既有行为，整理代码时
不要为了“看起来更合理”而调整调用顺序。

## VehicleControl 主流程

主函数内各段按覆盖优先级排列：

1. 路径安全停车、任务完成或 N 挡停车；
2. 两处场景化交通灯停车；
3. 空路径停车；
4. 计算相对路径位姿、期望速度和期望加速度；
5. 可选 ACC/AEB 诊断计算与基础纵向控制；
6. R 挡几何控制或 D 挡 Stanley 控制；
7. 曲率限速、传感器缓停和 GNSS 急停；
8. D 挡速度给定上升斜坡,再按原标定比例换算成油门；
9. 电子围栏与横向偏差停车覆盖；
10. 输出限幅及 R 挡油门覆盖；仅 D 挡积分过阈值后补刹，R 挡保持 09-19 修改前的控制。

后面的步骤可能覆盖前面的控制字段。修改某一业务条件前，应同时检查该条件之后所有对
`mControlData` 的赋值，不能只看局部代码。

## 起步速度给定斜坡（2026-09-19 调柔）

用户确认底层电机为速度环，油门与最终车速的比例已经实车标定。
保留 D 挡 `speed_cmd × 18`、R 挡 `mSpeed × 10`（上限 45%），以及原来的
0.5m/s 跟随间隙。只平滑 D 挡速度给定的上升，下降与停车指令立即生效。

`/robot/control/launch_speed_slope` 为速度给定上升斜率，默认从 0.3 降为 **0.15m/s²**，
按现有 20Hz 控制周期每次增加 0.0075m/s。持续目标不低于 1m/s、底层速度环能跟随时，
速度给定约 6.7s 升至 1m/s；这里描述给定变化率，实车瞬态还需现场验证。
参数每周期读取；非正数、非有限值回退至 0.15。车端若已有旧参数会覆盖源码默认值，
部署后应核对并按此次设置：

```bash
rosparam set /robot/control/launch_speed_slope 0.15
```

速度给定使用每个控制对象独立的 double 状态，最后才量化为 uint8 油门。
较小 slope 也能逐步累积，不会因每周期不足 1% 而卡在零。
原 5% 最小油门保留为目标约束，先换算到目标速度再走斜坡，起步期间不直接跳到 5%。
N 挡、任务停车、路径安全停车、空路径、交通灯停车、GNSS 急停、围栏与横向偏差停车
均清除斜坡历史；恢复后从零起步。R 挡保持原输出并清除 D 挡历史。
首次在 D 挡接入且车辆已运动时，从当前反馈车速衔接。

此前的 `throttle_slope`、`launch_speed_gap`、`launch_min_throttle` 三参数方案已回滚，
这些旧参数不再读取，也不更改原有标定。验证入口：

```bash
PYTHONDONTWRITEBYTECODE=1 python3 src/pnc/tests/control/verify.py --output /tmp/control_speed_verify
```

测试驱动真实控制源码与真实消息生成的 ROS 桩，覆盖斜坡累积、停车/换挡恢复、
低速保底和稳定输出；可加 `--baseline-control <旧 control_comply.cpp/.h 所在目录>`
进行新旧标定输出对照。09-19 C++11 控制节点编译/链接、80 项检查通过（含 19 项
旧版标定对照）。本机验证不能替代 ROS1/车载编译和路测。

## 普通 D 挡终点制动（2026-09-19）

规划端以 0.2m/s²、4s 余量和末段 d/8 提前减速，仍以 0.3m/s 蠕行至原 0.5m 到位区。
控制端 `TerminalStopBrake()` 仅在 TRACKPATH 任务完成、当前/期望挡位均为 D、目标零速、
到位距离处于 [0,0.5)m、真实 CAN 车速处于 (0.05,0.35]m/s 且反馈不超过 0.2s 时，
将最后一段刹车按 100%/s 建立：首帧 5%，正常 20Hz 时每帧增加 5%，约 0.8s 达到 80%。
按真实时间计算；控制卡顿不会重新从低制动逐帧累积。全程油门为零，不延迟任务完成。

车速降至 0.05m/s 即切换原 80% 保持。反馈无效/超时、车速较高、时钟回退、N/R 挡、
其他作业任务或已有制动均保持原停车处理；safety、CAN 急停、传感器/网络故障、规划心跳、
围栏和横向偏差也会禁止此缓刹。此处不改变规划的障碍物判据、D×18/R×10 标定或消息。
制动百分比不等于实际减速度，实际液压响应、载荷和末段停车位置仍需实车验证。

## D 挡减速积分补刹（2026-09-19）

仅自动驾驶、D 挡有减速需求时启用积分。使用 `dec = 当前 CAN 车速 - speed_cmd`，
单位为 m/s；**不设 0.5 或 0.05m/s 等速度差门限**，任意正误差立即开始积分。
`speed_cmd` 已应用跟随间隙、曲率和传感器故障限速，尚未应用起步上升斜坡，
避免将起步斜坡本身误判为减速需求。没有使用存在历史问题的 `desireAcc`。

`UpdateBrakeIntegral()` 按实际时间累计 `I += dec * dt`，单位为 m。
默认门槛按用户要求降低为 **0.1m**，ROS 参数为 `/robot/control/brake_integral_threshold`，
通过 `getCached` 读取，可在运行时调节；非有限、非正或大于 10m 的值回退 0.1m。
首个有效周期建立时间起点，重复时间不增加积分。积分严格超过门槛前，普通减速仅通过
throttle 的底层电机速度环；D 挡旧的速度差超过 1.5m/s 小刹车也不再绕过积分门槛。
在标准 20Hz 控制下，持续 0.6m/s 误差约 0.2s 后介入，持续 0.5m/s 误差约 0.25s 后介入。
这些是合成恒定误差下的指令介入时间，不是实车液压响应时长。

```bash
rosparam set /robot/control/brake_integral_threshold 0.1
```

积分超过门槛后，刹车按 `dec * 50` 与本周期原刹车取较大值，上限 100%，
四舍五入为整数百分比；整数协议下最小 1%，避免微小误差量化成零。
补刹时在最终油门赋值后清零油门，只发布一条无驱动的制动消息。
例如当前 1.0m/s、目标 0.4m/s，先由电机减速，误差持续至门槛后补刹 30%。
系数按用户最新要求从 30 调为 50，只提高接入后的制动比例，不调整积分接入时机。
积分最多保留两倍当前门槛，刹车比例不按周期累加。

减速需求消失（`dec <= 0`）、进入手动、换挡、任务 ID/类型/期望挡位改变、
以及进入 safety/终点/交通灯/空路径/GNSS/围栏/横向偏差停车时清零积分。
同一任务或规划消息重复发布不会清零。CAN 反馈超过 0.2s、时间回退或控制间隔超过 0.2s 时，
不累计未观测时间：尚未介入的积分重置，已经介入的补刹在正误差仍存在时保持，
不会单凭断流释放刹车。CAN 急停状态也不累计普通减速积分。

**D 挡** `safety=1` 在函数入口直接输出零油门、100% 刹车并返回，完全不等待积分；
GNSS、围栏、横向偏差、原任务/终点、N 挡、交通灯及空路径的独立停车保持。
**R 挡不使用积分，也不执行今天新增的比例补刹**。按用户的挡位范围要求，
R 挡恢复 09-19 首次修改前的速度环、速度差超过 1.5m/s 的原有小制动，
以及原 `|目标速度| < 0.1 && safety` / `Path_Id == 5 && safety` 停车分支。
因此 D 挡无条件优先处理 safety 的扩展也只作用于 D，不改 R 挡原有判定。
D×18、R×10 的速度给定标定、D 挡起步上升斜坡和低速终点缓刹均保持。

日志输出 `dec`、`brake_integral`、`brake_active` 及最终刹车比例。
运行 `tests/control/verify.py` 验证真实消息发布，覆盖不同周期/阈值、小误差、
同时间重复执行、重置/断流、制动恢复及安全覆盖。`--baseline-control` 应指向
09-19 首次修改前的 control 目录，不能用今天已加入 R 挡补刹的中间版本作基准。
对照包含 R 挡完整消息字段及发布顺序，覆盖起步、减速、终点、safety、故障和 ACC。
本机未连接车辆，最新结果见根目录 workflow.md。

## 常用业务修改入口

2026-09-18 配合规划的路线内末端轨迹，纯追踪前馈距离改为从车辆投影里程开始计算，
不受车后拟合点数量影响。前方轨迹短于前视距离时选择真实末点，车辆与末点重合时
返回零前馈，避免使用默认 `(0,0)` 或产生 `0/0`。纵向速度标定和停车制动覆盖保持。
规划/控制分进程的消息交接验证见 `tests/planning/terminal_stop.cpp` 和
`terminal_control.cpp`，由 planning 的 `verify_point_speed_limit.py` 一并运行。

同日复核补齐 R 挡末端控制：前方不足 10 个插值点时，只要还存在有效末端线段，就继续
计算倒车转角；预瞄包含真实末点，路径短于 3 m 时选末点，去掉原来的末端减 4/5 索引。
空/单点和与目标重合时返回零角。目标恰在车辆纵向轴上时返回直行，取消人为添加 5 cm
横向偏差，避免短路径把该偏差放大成大转角。左右圆弧、0/90/180/270/360° 直线、六组
真实规划发布的倒车弯道末端消息均纳入检查；没有调整纵向标定或转角限制。

- 改路径点接收、过滤或样条：`ControlComply::SetPathPlanData`
- 改停车优先级和安全覆盖：`ControlComply::VehicleControl`
- 改围栏判定：`ControlComply::FenceAlarm`
- 改 D 挡横向算法：`LatController::calculate`
- 改 R 挡横向算法：`GeometricConstrol::LateralControlTrack1`
- 改基础油门/刹车分配：`SpeedControl::SpeedTrack`
- 改 ACC/AEB：`ControlComply::LongitudinalFeedforwardControl`
- 改最终消息发送方式：`ControlComply::PublishMessage`

## 修改时必须保留的既有语义

- ROS 话题使用绝对名，include 顺序不调整。
- 不重命名既有标识符，包括 `GeometricConstrol`、`setTaskPlanData` 等历史名称。
- `VehicleControl()` 内逻辑顺序是控制优先级的一部分。
- `PublishMessage()` 在油门和刹车同时非零时会拆成两条消息发布。
- D/R 挡使用不同的横向控制器，不能通过表面相似直接合并。
- D 挡 ×18、R 挡 ×10 为用户确认的速度环标定比例,起步调参只调整速度给定斜率。
- 多处算法含跨周期 `static` 状态；移动实现时必须保持函数和静态对象语义不变。
- ACC/AEB 使用 `.inc` 是为了保持原翻译单元；不要直接将它加入 CMake 独立编译。
- `mControlData` 字段赋值是对外协议行为，清理时不能删除。

## 已知但本轮未修改的问题

- `SpeedControl::m_acc_last` 未在构造函数中初始化，而
  `AccelerationCalculateBySpeed_P()` 最终会把它赋给 `desireAcc`。该发布字段会随
  对象初始内存变化；基础油门/刹车当前不使用传入的 `tAcc`，但外部仍可观察该字段。
- `ControlComply::mPathid` 和 `mPathsafety` 也未在构造函数中初始化，首条有效路径消息
  到来前读取它们存在风险。

这些属于既有行为和独立缺陷，当前整理没有擅自初始化；若要修复，应单独做业务影响确认和
新旧场景验证。
