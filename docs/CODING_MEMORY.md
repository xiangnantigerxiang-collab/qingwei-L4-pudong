# 编码与技术风格记忆

更新：2026-09-20。适用：本工程。每次编码任务前完整阅读。
本文件是随工程持久保存的偏好与约束，不依赖聊天上下文；不承诺工程之外的工具自动加载。

## 恒定准则：时间复杂度与车载 CPU

用户于 2026-09-20 明确要求：车载 CPU 负荷已经接近饱和，内存尚有余量；修改代码时
尽量减小时间复杂度，可以通过增加空间复杂度换取时间复杂度。
**每次开始代码修改任务前，必须重新读取本节；同一会话开始新的修改任务时也不省略。**

- **优先节省 CPU。** 在业务语义和安全判据保持正确的前提下，优先选择时间复杂度更低的
  方案；复杂度相同时减少实际计算量、重复遍历、数据复制、堆分配及高频日志。
  特别关注规划、控制和消息回调等高频路径，避免无必要的每周期全量扫描或重复计算。
- **允许有界空间换时间。** 优先复用已有结果、预计算、缓存、索引及预分配容量；
  与输入数据有关而与本周期无关的计算，尽量放到数据变更时执行。说明缓存的容量上限、
  内存开销与回收方式，不能以无界历史积累换取局部提速。
- **缓存必须及时失效。** 明确结果依赖的路径、任务、定位、挡位或参数等实际输入；
  相关输入变化、任务复位或数据失效时及时重算或清除。不得沿用旧 safety 结论，
  不得因清理本项缓存而解除其他来源的 safety，不能为提速改变安全距离、触发时机或业务流程。
- **修改前后都核算复杂度。** 定义输入规模 N，检查新增时间/空间复杂度、执行频率和
  最坏情况；使用缓存时同时说明重建成本与命中成本，区分最坏、摊还和典型情况。
  全量哈希、比较或扫描后再命中缓存仍有 O(N) 成本，不能宣称为 O(1)。
  不可避免的新增开销如实说明，不把该准则解释成所有计算必须 O(1)。
- **性能结论要有证据。** 涉及高频路径开销或以性能优化为目的的修改，用相同输入作
  等价性与耗时对照，关注延迟峰值/尾部、分配次数和内存峰值，不能只报平均值。
  没有实测就明确说明；本机结果不等于车端结果，不能凭复杂度或路径短就断言 CPU 开销可忽略。
  保持既有线程模型、话题频率和业务修改边界，不借性能需求进行无关重构。

## 依据与优先级

优先级为：用户当前明确要求 → 同一事项最新有效更正 → 本文件和模块规范 → 邻近代码习惯。
历史采样只描述已有代码，不把缺陷变成新增代码的要求。发现文档和代码不一致时，分别记录
“用户要求”和“当前实现”，不能靠整理文档偷偷改变实现，也不能把旧文档当作现行事实。

| 来源 | 应长期保留的偏好 | 适用边界 |
|---|---|---|
| 2026-09-20 恒定准则 | 每次改代码前重读性能准则；优先降低时间复杂度，允许有界空间换时间 | CPU 接近饱和、内存有余量；保持 safety 语义并及时清除失效状态 |
| 2026-09-19 多次强调 | 只改指定模块和指定挡位，明确说明对其他业务的影响 | 当天新增起步/减速/刹车仅 D，R 原行为保留 |

## 编码表达

- 语言和工具优先沿用工程现有选择：PNC/canbus 为 ROS1、C++11；Web/记录模块沿用
  现有 Python 标准库与 rospy。不要为局部需求引入新框架、线程模型或无关依赖。
- PNC 统一写法：4 空格，`if(condition) {`、`} else {`，函数/类左大括号同行。
  canbus 的函数/类括号遵循其专用指南和修改点上下文；不借格式整理统一两个模块。
- 新类/方法采用现有 PascalCase，PNC 成员常用 `m` 前缀、输入参数常用 `t` 前缀、
  局部变量用 snake_case。已有名字即使拼写不理想也不擅自改，消息字段视为协议。
- 保持 include 顺序、`.inc` 包含位置、命名空间及跨周期状态的生命周期。
  `.inc` 不作为单独编译单元加入 CMake。
- 中文注释优先解释原因、单位、坐标系、边界和安全覆盖，不复述赋值动作。
  新增重要阈值使用有含义的局部常量或现有参数通道；不批量抽取旧魔法数。
- 不复制未初始化、缺少输入校验、半更新状态或高频刷屏等历史缺陷。
  诊断跟随模块日志方式，在变化或限频时输出。

## 技术与业务习惯

1. **先追踪完整链路。** 看发布者、订阅话题、过滤、单位转换、跨帧状态、最终覆盖和控制输出。
   监控“看见障碍物”不代表规划的专用输入有效；不能只改最先搜到的常量。
2. **模块职责清楚。** ROS 接线保持薄层，业务在既有 Comply/core，算法按职责拆分；
   不把 canbus 已回退的 core 结构当作现行架构，不为了新需求重建整套封装。
3. **安全来源叠加。** 普通限速取较小值，独立 safety 按既有规则叠加；不得解除其他来源停车。
   保持急停、积分补刹、普通减速和终点缓刹各自优先级，R 不继承仅为 D 增加的分支。
4. **状态和时间明确。** 连续帧应是真实不同帧，重复时间戳不能加票；说明超时、重置、
   任务切换、手动/自动、D/R/N 和解除迟滞。按实际时间做积分和平滑，注明单位。
5. **几何和速度明确。** 说明地图系/车体系、北零顺时针 heading/数学 yaw、物理框朝向/
   运动方向、绝对速度/接近速度。`dec` 在当前补刹代码中是速度误差 m/s，不是 m/s²。
6. **保留标定与数据。** 用户的 CSV、YAML、地图、外参、协议和运行文件不因清理被重写。
   涉及这些内容时，只改本次需求所需的明确范围。
7. **性能遵循上述恒定准则。** 复用向量容量、固定 ID 表、几何缓存和空间索引；说明最坏情况和缓存峰值。
   保持现有单线程调度和话题频率，避免每周期文件读取或新增阻塞操作。
8. **跨包消息一起核对。** 修改 `.msg` 前搜索全部同名副本及读写方；can_msg/can_comm_msg
   涉及 canbus、pnc、simview。不能只让一端编译通过，也不能依赖“字段碰巧相同”。

## 工作与交付方式

- 用户说“帮我修改/增加”即执行；已授权范围内连续完成，不反复确认。
- 非 git 环境先备份。只读定位和可逆修正可继续推进；不要覆盖用户另行编辑的文件。
- 调参先说明默认值/运行值、参数在哪读取、热更新还是重启生效、是否需要重编。
- 验证选择与变化匹配：文档查链接和事实；算法查边界；状态机查跨帧；安全改动查
  优先级和未改挡位；性能改动做等价对照。不要用只复述实现的测试代替业务验收。
- ROS 桩从真实 `.msg` 生成；本机工具链可能需 C++14，不因此升级生产 C++11。
  不能把桩编译、理想跟随仿真、历史测试数或 x86 性能写成 Orin 实车结论。
- 默认中文，先说明结果，再说明范围与证据。文件清单分业务、测试、文档，标明新增/删除；
  用户问位置时给当前文件和行号。对未验证或尚不确定的点直说。
- 文档维护是修改内容的一部分：更新唯一现行说明，历史归档只保留结论和证据入口。
