# 导航速度切换复核（2026-09-21）

结论：发现并修复一类导航异常值处理遗漏，涉及最终规划和控制输出；在同速度输入对照中，
未发现其余业务回归。原修改后的1566文件哈希在本次开工时一致，没有覆盖用户后续改动。

## 已复现并修复的问题

1. 控制：CAN=1m/s、导航位置/航向有效、速度变为NaN时，切换前转角仍为有限值，
   切换后出现 `throttle=15, brake=0, wheelAngle=NaN`。仅检查补刹/终点函数不足以保护转向。
   `control_comply.cpp::VehicleControl()` 现于行驶计算前检查有限值，异常时零驱动、100%制动、
   零转角/速度目标/期望加速度并复位普通控制历史。原 safety、终点/N挡、红灯、空路径分支
   仍先处理；原终点异常反馈的80%保持继续通过，未将该业务改为100%。
2. 规划：已完成起步观察的兼容链中，导航NaN/正无穷仍可发布非零速度，负无穷可发布
   `safety=0, desireSpeed=-Inf`。`path_plan_output.inc::PublishFinalPlanPath()` 现独立叠加
   安全零速，覆盖D/R和提前返回。按原输出覆盖方式恢复内部值，不留下新的安全闩锁。

两处都不回退已弃用的CAN速度；有效导航恢复后仍服从原停车、斜坡和其他安全来源。
检查只改变异常速度下的指令；实际速度遥测保留输入读数，用于区分无效输入与真实静止。
规划记录限频的 `invalid_navigation_speed` 原因，控制使用限频ROS告警，没有恢复编号调试打印。

## 正常业务差分

以导航切换前快照 `navigation_speed_before_20260921_081522.tar.gz` 为基准，两版使用相同
CAN和导航实际速度、同一套任务/位姿/传感器输入，比较实际发布内容和状态：

| 检查 | 结果 |
|---|---|
| 控制126组常规/低速/补刹/终点/安全用例 | 3737条消息一致 |
| R挡15类场景×4组数值 | 2460条消息一致 |
| 规划任务/挂脱钩/碰撞/R挡/暂停/急停/轨迹复用及固定种子场景 | 387组状态、635条路径消息、48条速度记录、参数事件共6054行逐字节一致 |
| 其他CAN字段 | 挡位、转角、模式、急停、挂钩、载荷读写保留 |
| 云端心跳 | 仍从规划curSpeed×3.6输出km/h，只改变实测速度来源 |
| can_comm及底盘消费 | vehicleSpeed沿用转发；底盘控制帧不消费该字段，不改变执行器编码 |
| HDMap | 无CAN实际车速入口；源码、地图、SDK算法/库未改 |

控制差分只排除按需求新增赋值的 `control_msg.vehicleSpeed`（原为默认0，现在为导航值），
油门、制动、转角、目标、偏差、其他字段及发布次序均比较。来源冲突另有18组216条全消息对照，
使用0、99、负数和NaN/Inf的CAN速度，验证其不影响相同导航输入下的控制结果。

规划首次差分定位到旧随机夹具只改了导航字段、CAN仍为0。现同时设置两路相同实际速度，
避免把不同输入误判成无关业务回归；来源隔离专项继续分别发送矛盾输入，没有用同值测试替代。

## 明确的行为变化与验证边界

- 本任务本来就会使实际速度判断服从导航，不能要求CAN和导航不一致时控制输出保持旧值。
- 起步仍严格>0.2m/s连续两帧，但计票源从CAN改为导航；两路频率不同，实际退出时延可能不同。
- 积分/终点缓刹同时检查导航和CAN接收年龄≤0.2s，导航断流不能靠CAN重发继续计入积分。
  这不等于新增了覆盖所有控制路径的导航断流急停。
- navigation节点仍会50Hz重发缓存数据；接收时效不能识别冻结测量。planning原有定位健康
  检查基于 `/localization`、超过2s或status=2走原GNSS故障链，本轮没有改变该策略。
- ultra沿用原速度缓存和单向起步闩锁，没有新增独立速度老化。不能将本轮接线测试视为此项已修复。
- 历史起步完整套件仍有2m预期，而当前源码为1m；保留差异，只运行其适用的左二专项。
- 本机无ROS1，以上为真实源码加消息桩验证，未进行车端构建、部署或实车测试。
